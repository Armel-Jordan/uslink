# Expo HAS CHANGED

Read the exact versioned docs at https://docs.expo.dev/versions/v57.0.0/ before writing any code.

# UsLink conventions

- **Routing**: expo-router with `Stack.Protected` guards. Two gates: session (`src/app/_layout.tsx`) then link (`src/app/(app)/_layout.tsx`). Tabs come from `expo-router/js-tabs` — the bare `Tabs` export from `expo-router` is deprecated in SDK 57.
- **Data access**: screens only ever call `data` from `@/lib/data`. Two implementations satisfy `DataAdapter` (`data/supabase.ts`, `data/demo.ts`) and the choice is made once at startup from `EXPO_PUBLIC_SUPABASE_URL`. Never import `@/lib/supabase` from a screen, and never branch on "is there a backend" in UI code.
- **Copy**: no literal user-facing text in components — screens import `t` from `@/lib/strings` and never know which language is active. The dictionaries live in `src/lib/i18n/`, one file per language (fr, es, pt, it, ar, zh, ja), every one typed `Dictionary` against `fr.ts`, so an incomplete translation does not compile. Adding a string means adding it to all seven.
- **Plurals go through `Intl.PluralRules`, never through `n <= 1`.** Arabic has six CLDR categories, Chinese has one. `makePlural` in `src/lib/i18n/plural.ts` is the only way to build a count-dependent string.
- **`npm run check:i18n` catches what `tsc` cannot**: a translated function that dropped its placeholder. `greeting: () => "Hola"` compiles fine and renders a greeting with no name.
- **The couple shares one language, like it shares one clock** (`links.locale`). The daily question, the fallback bank and the AI generation all follow the link's locale — never the device's. `src/lib/prompt-library.ts` is the single fallback bank; the Edge Function deliberately has none, because a duplicated one served French under an Arabic interface.
- **Styling**: `StyleSheet` + tokens from `src/constants/theme.ts` (`Colors`, `Spacing`, `Radius`). Colours come from `useTheme()`, never hardcoded, and every key exists in both light and dark.
- **The reveal rule is a database rule.** A partner's answer becomes readable only once you have answered, enforced by the `answers_select` RLS policy in `supabase/schema.sql`. Do not re-implement or weaken it in the client.
- **Every visibility rule belongs in the database, and every database rule gets an assertion.** `supabase/tests/rls.test.sql` is the executable statement of what the schema promises; `npm run test:rls` runs it against a real Postgres (PGlite, WebAssembly — no Docker, no CLI). Touching a policy, a `security definer` function or a migration means adding or updating an assertion in the same change.
- **Two sources of schema truth, kept identical by test.** `supabase/schema.sql` provisions a fresh project; `supabase/migrations/*.sql` moves an existing one. `node scripts/rls/run.mjs --baseline=<ref>` proves the two converge on the same policies, functions, triggers and constraints, and that existing rows survive. Run it whenever you add a migration.
- **Any view exposed to `authenticated` must carry `with (security_invoker = true)`.** Without it the view runs as its owner, PostgREST exposes it, and a single `GET /rest/v1/<view>` reads every couple's answers — the reveal rule annulled in one line. Likewise, a `security definer` function granted to `authenticated` starts with an `is_link_member` early-return guard, never a predicate buried in a CTE.
- **AI stays server-side.** The Anthropic key lives in Supabase secrets; the model is called only from `supabase/functions/daily-prompt`. Model id is `claude-opus-5` with `output_config.format` (JSON schema). Any failure path must fall back to `prompt-library.ts` rather than leaving a day without a question.
- **Before committing**: `npm run typecheck`, `npm run test:rls` **and** `npm run check:i18n`. `supabase/functions` is Deno and excluded from `tsconfig.json` on purpose — nothing typechecks it, and nothing typechecks SQL either, which is exactly why the RLS suite exists.
